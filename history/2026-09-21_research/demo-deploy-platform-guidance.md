# Platform guidance for DemoDeployPipeline review

Verified against Microsoft primary sources on 2026-09-22. This is a platform reference for the repository review, not evidence that the demo implements these controls or has been run successfully.

## Fit with the agreed constraints

- **Dataverse metadata is required.** Microsoft's solution-based ALM requires a Dataverse database in participating environments. SharePoint can remain the business-data store, but describe the architecture as “no business data in Dataverse,” not literally “no Dataverse.” [ALM overview](https://learn.microsoft.com/en-us/power-platform/alm/overview-alm)
- **Use unmanaged in Dev and managed in Test/Prod.** Exported unmanaged packages preserve the editable source; managed packages are deployment artifacts. A managed solution cannot itself be exported, so a Test-to-Prod promotion must reuse the artifact exported from Dev. Updates retain components omitted from the new package; upgrades support removal, so deployment mode must be deliberate. [Solution concepts](https://learn.microsoft.com/en-us/power-platform/alm/solution-concepts-alm)
- **Managed solutions and Managed Environments are different.** Native Power Platform pipelines require Managed Environments for non-developer target environments; Microsoft documents automatic enablement beginning February 2026. That prerequisite concerns the native pipeline feature. A custom export/import workflow is a different implementation and can use managed solution packages without choosing native pipelines. The latter is an architectural inference from the separate feature requirements, not a claim that this demo's tenant configuration is validated. [Pipelines overview and FAQ](https://learn.microsoft.com/en-us/power-platform/alm/pipelines)
- **Promote the same package.** Microsoft's native pipelines deliberately preserve one artifact through sequential stages without re-exporting. Apply that property to the custom process: store both exports once, approve a particular managed file/version, and import that exact managed file into Test and Prod. SharePoint with versioning/restricted release folders is an interim artifact archive; calling it equivalent to Git/source control would overstate its capabilities. The SharePoint archive recommendation is our design judgment. [Pipeline artifact behavior](https://learn.microsoft.com/en-us/power-platform/alm/pipelines)

## Implementation checks that matter

1. **Check actual connector/action names.** Current action catalogs for [Power Apps for Makers](https://learn.microsoft.com/en-us/connectors/powerappsforappmakers/) and [Power Platform for Admins](https://learn.microsoft.com/en-us/connectors/powerplatformforadmins/) do not list solution import/export actions. Dataverse exposes those platform operations through unbound actions. The [Microsoft Dataverse connector](https://learn.microsoft.com/en-us/connectors/commondataserviceforapps/) is classified Premium and supports an unbound action in a selected environment. “Only SharePoint business data” does not make a Dataverse-based deployment flow standard-connector-only.
2. **Distinguish submission from completion.** `ImportSolutionAsync` returns job identifiers, not a completed deployment. Track `AsyncOperationId`; Microsoft's example uses completed state `3` and successful status `30`, and reads import logs through the import job key on failure. Asynchronous exports likewise require completion before downloading via `DownloadSolutionExportData`. A custom flow should bound its polling and preserve failure/timeout status instead of recording success when the initial action returns. [Asynchronous import/export](https://learn.microsoft.com/en-us/power-platform/alm/solution-async)
3. **Supply target configuration explicitly.** Connection references and environment-variable values require target-specific mappings. Microsoft's deployment settings JSON illustrates separate `ConnectionReferences` and `EnvironmentVariables`; connections must already exist and be usable by the connection-reference owner. Exported references are not portable credentials. [Deployment settings](https://learn.microsoft.com/en-us/power-platform/alm/conn-ref-env-variables-build-tools)
4. **Use supported import parameters where possible.** `ImportSolutionAsync.ComponentParameters` accepts environment-variable and connection-reference overrides. The action separately exposes activation, unmanaged-customization overwrite and holding-solution options; these choices should be intentional rather than hidden defaults. [ImportSolutionAsync action](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/importsolutionasync?view=dataverse-latest)
5. **SharePoint is a separate deployment dependency.** SharePoint data-source environment variables identify Site and List, and matching source/target column names and internal metadata matter. Consequently a solution ZIP and changed URL alone are insufficient to establish the target SharePoint schema. Provision/migrate lists, columns and permissions separately and test the actual app against the target lists. [Environment variables: SharePoint](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/environmentvariables)
6. **Connection identity and licensing identity are different.** Automated/scheduled flows generally use owner licensing context, while instant/button/Power Apps flows use invoking-user context unless a qualifying flow-level license applies. A service-account connection is not a blanket license for every caller. Verify the demo trigger type, owners and actual licenses; do not infer compliance solely from the connector credential. [Power Automate licensing FAQ](https://learn.microsoft.com/en-us/power-platform/admin/power-automate-licensing/faqs)

## Recommended review baseline

One release record should identify solution/version, immutable unmanaged and managed package locations, target configuration, Test results/approval, final import status and Prod verification. Block promotion on import failure, timeout or absent approval. Validate the actual target solution version and flow/app operation after import. These are recommended controls derived from the platform behaviors above, not requirements for adopting Git or Managed Environments.
